# ファミコン汎用ダンプ機 — Uno + Nano + 裸328P

ロジックIC不使用。3台の ATmega328P に 48 本の信号を分担させ、I2C で束ねる。

## 構成

| チップ | 担当 | I2C |
|---|---|---|
| Uno | PRGアドレス A0-A14、CHR A12、PCとのUSB窓口、I2Cマスター | — |
| Nano | PRGデータ D0-D7、制御4線、CHRデータ上位4bit(D4-D7) | 0x20 |
| 裸328P | CHRアドレス A0-A11、CHRデータ下位4bit(D0-D3) | 0x21 |

### CHR A12・D4 は裸328Pから移設済み(2026-09-03)

裸328Pの PB0(14番/CHR A12)と PB5(19番/CHR D4、ISPのSCKと兼用)が、
どちらも「High/Lowを命令しても電圧が動かない」故障を起こした。カートを外し
電源のみ入れた単体状態でも再現し、3枚のチップ全てで同じ壊れ方をしたため、
最終的にはチップの故障ではなく**328Pのソケット周りの配線が他の信号線と
物理的に接触していたこと**が原因と判明した(新しい線に交換しても直らず、
配線そのものをやめてカート端子へ直接半田付けしたら解決した)。

- A12 → **Uno の A3(PC3)** へ移設。328Pの14番は未使用のまま放置してよい
- D4 → **Nano の D1(TX)** へ移設。D0(RX)ではなくD1を選んだのは、USBシリアル
  変換チップから見てD0は常に駆動される出力側、D1は受信専用の入力側だから
  (駆動衝突を避けるため)。328Pの19番は未使用のまま放置してよい

いずれも、移設元のピンは**配線を完全に外すこと**。繋いだままだと壊れた
ピンと移設先の新しい駆動が同じ線を取り合う形になる。

判断はすべて PC 側(`fcdump.py`)に置く。装置はマッパーを知らず、
「このCPUアドレスを読め/書け」しか受け付けない。
SFC-CIC で「成立したかを装置に判定させた」のが誤検出5連発の原因だったので、
同じ轍は踏まない。

## 設計上の確定事項

### CHR A13(カート56番)はアドレス線ではない

PPU のアドレス空間は `$0000-$1FFF` がパターンテーブル、`$2000-$3FFF` が
ネームテーブルで、**A13 がその境目**。標準基板は CHR ROM の `/CE` を56番に、
コンソールの CIRAM `/CE` を49番(`/A13`)に繋いでいる。

つまり **CHR ROM の窓は A0-A12 の 13 本 = 8KB** で、56番は読み出し中ずっと
Low に張る「実質チップイネーブル」。8KB を超える CHR はマッパーでバンクを切る。

配線(56番 → Nano A3)はそのままで正しい。役割だけが違う。

### 未結線ピンのうち2本は浮かせてはいけない

コンソール → カート方向の入力なので、開放だと不定になる。

| ピン | 信号 | 対処 |
|---|---|---|
| 47 | VRAM /WR | **10kΩでVCCへ**。CHR-RAM基板への誤書き込みを防ぐ |
| 49 | CHR /A13 | **10kΩでVCCへ**。A13=0 の相補値 |

15(/IRQ)・18(VRAM A10)・48(VRAM /CE)・45/46(SOUND) はカート側の出力なので開放でよい。

### 読みは静的が既定

ROM は静的デバイスなので、M2=High / /ROMSEL=Low を保ったままアドレスだけ
変えれば読める。1バイトあたり I2C 1往復で済む。
マッパーが M2 のエッジを欲しがる場合のために `set_cycle(1)` でパルス読みにできる。

### 書き込みは /ROMSEL の立ち上がりで確定させる

実機の `/ROMSEL = !(A15 & M2)` に合わせ、`/ROMSEL↑` と `M2↓` の順で解除する。
多くのマッパーはその立ち上がりで値を latch する。データ線はそのエッジを跨いで有効に保つ。

### 328Pは水晶の周波数に依存しない

今回使う個体は標準的な **16MHz水晶**(Arduino標準・F_CPU既定値どおり)。
以前SFC-CIC用に組んだ21.585MHz(AD21L4)の個体とは別物だが、そもそも
`fc_chr328` はどちらの周波数でも動くように書いてある。

1. TWI のスレーブは SCL をマスターに叩かれて動くので、こちらのクロック精度は無関係。
   条件は「F_CPU ≥ SCL×16」だけで、16MHz でも 21.5MHz でも満たす
2. `fc_chr328` は `delay()`/`micros()` を使っていない。ROM のアクセス時間は
   次の I2C トランザクション(数十µs)が勝手に稼ぐ

16MHz個体であれば `arduino:avr:uno` の既定F_CPU設定のまま(今回書き込み済みの状態)で正しい。

## 書き込み

```bash
arduino-cli compile --fqbn arduino:avr:uno              fc_uno
arduino-cli upload  --fqbn arduino:avr:uno -p COM8      fc_uno
```

```bash
arduino-cli compile --fqbn arduino:avr:nano:cpu=atmega328         fc_nano
arduino-cli upload  --fqbn arduino:avr:nano:cpu=atmega328 -p COM9 fc_nano
```

裸328Pはブートローダを使わず ISP で入れる(ArduinoISP を書いた別のArduino経由)。
ヒューズには触らないので、設定済みの外部水晶モードはそのまま残る。

```bash
arduino-cli upload --fqbn arduino:avr:uno -p COM9 -P arduinoasisp fc_chr328
```

## 立ち上げ手順

配線を51本引いた直後に「吸えるか」を試すのは順序が逆。止まった状態から確かめる。

**1. I2Cだけ確認**(カートは挿さない)

```bash
python fcdump.py --port COM8 ping
```

`{'nano': True, 'chr328': True}` が出ない場合は SDA/SCL の入れ違いか
プルアップ(3kΩ)を疑う。

**2. アドレス線をテスターで追う**(カートは挿さない)

```bash
python fcdump.py --port COM8 walk 3
```

PRG A3 だけ High になる。0〜14 で1本ずつ、カート側の端子で当たる。
`walk 99` で全部 Low。**ここを飛ばすと、あとで「読めない」原因が
配線かファームか切り分けられなくなる。**

**3. カートを挿して健全性ゲート**

```bash
python fcdump.py --port COM8 selftest
```

見るのは電圧ではなく機能。

- RESETベクタ(`$FFFC`)が `$8000-$FFFF` の中を指しているか
- 同じ16バイトを2回読んで一致するか
- 全部 `FF`/`00` になっていないか

通らないうちはダンプに進まない。

**4. ダンプ**

```bash
python fcdump.py --port COM8 dump nrom xevious.nes --mirror h
```

## 既知の制限

- **ミラーリングは自動判定できない。** カート18番(VRAM A10)はカート側の出力で、
  今の配線では繋いでいない。`--mirror h|v` で指定する
- **状態表示用のLEDが無い。** Uno の D13 は PRG A11、Nano の D13 は VRAM /RD に
  取られている。どちらも常に出力なので線を乱すことはないが、
  基板上のLEDは信号と一緒に光るだけで意味を持たない
- **速度**は I2C 100kHz で PRG 約0.25ms/byte、CHR 約0.75ms/byte。
  PRG 32KB で約8秒。立ち上げが済んだら `Wire.setClock(400000)` で4倍になる
- **対応マッパー: NROM(mapper 0)・Mapper 87・MMC3(mapper 4)・CNROM(mapper 3)・Sunsoft-1(mapper 184)・UNROM(mapper 2)・MMC1(mapper 1)。**
  MMC1は2026-09-04に大きく前進した:
  - **書き込みタイミングを修正**(sanniのcartreader実装より): `/ROMSEL↑`と
    `M2↓`を2回に分けて切り替えていたのが原因で、MMC1+SRAM基板(SNROM等)
    への書き込みが化けて何も反映されないように見えていた。`prgWriteCycleFast`
    (fc_nano.ino)で1回のポート書き込みに統合して解決。`mmc1_write()`は
    常にこちらを使う
  - **PRGモード値の誤り訂正**: nesdev仕様では2="$8000固定・$C000で切替"、
    3="$C000固定・$8000で切替"。逆に覚えていた
  - **SEROM基板(ドクターマリオ等)に対応**: この基板はMMC1からのPRGバンク
    切替線がPRG ROMに配線されておらず、PRGは32KB固定(NROM同然)。
    `--prg-fixed`を付けること(sanniのcartreaderのissue #1060で報告されている
    既知の構成)
  - **8KB CHRモードの下位bit無視**に対応: CHR0レジスタは8KBモードだと
    下位1bitを無視するので、8KB単位のバンクを選ぶには2ずつ進めて書く
    (`n*2`)必要がある
  MMC1(mapper 1)は実装したが**バンク切り替えが実機に反映されない不具合が
  未解決**(2026-09-04)。5回シリアル書き込みは装置側では正常に受理される
  (例外は出ない)のに、読み出す内容がバンク番号を変えても変化しない。
  原因不明、要調査
- `$8000-$FFFF` 内でアドレスの上位ニブルを跨ぐ読み(典型例: `$Bxxx→$Cxxx`)は
  読みが化けることがある(ダックハントの調査で確認)。`$BFFF→$C000`は
  A0-A13の14本がほぼ同時に反転する最悪条件で、同時スイッチングノイズ
  (SSN)が原因と推定している。**この化け方は完全に決定論的**(毎回同じ
  バイトが同じ値に化ける)なため、「再読して一致するか」という検証では
  検出できない — 2026-09-04、ダックハントで2回独立にダンプしたデータが
  ビット単位で完全一致したにもかかわらず、両方とも実機(RetroArch)で
  起動しなかった。検証コードは可能な場合、生の`$C000`/`$E000`直読みを
  避け、既に使っているバンク窓経由の再読みで代用している
  (`verify_prg_mmc3`, `dump_mmc1`内の検証を参照)。ただしNROM16KB
  (ダックハント等、RESETが`$C000`直撃)はバンク窓による迂回ができず、
  現状ダンプ不可。ファームウェア側でアドレス変更後に数µsの settle
  待ちを入れる対策が候補だが未着手

## 次にやること

1. **ドラゴンクエストIVが実機で起動しない問題。** ダンプデータは逆アセンブル
   で正しいと確認済み(RESET/IRQベクタとも正当なコード)。SUROM基板の
   512Kフラグ(`$A000`のbit4)対応、バッテリーフラグ付与、どちらも効果なし。
   Mesen自体は`Mapper: 1 Sub:0`、`PRG ROM: 512 KB`と正しく認識している。
   原因未特定
2. **ダックハントの`$Bxxx→$Cxxx`境界バグ。** 決定論的(同じバイトが毎回
   同じ値に化ける)なので再読み検証では検出できない。原因未特定、
   RESETが`$C000`直撃のためバンク窓による迂回も使えない
3. 通ったら I2C を 400kHz へ

## ファイル

- `fc_uno/` — マスター。PRGアドレス・CHR A12とPC窓口
- `fc_nano/` — PRGデータ・制御線・CHR上位4bit(D4-D7)
- `fc_chr328/` — CHRアドレス・CHR下位4bit(D0-D3)
- `fcdump.py` — ホスト側。判断はすべてここ。マッパー別のダンプ手順もここ
  (`dump_nrom` / `dump_m87` / `dump_mmc1` / `dump_mmc3`)
- `dp100.py` — Alientek DP100をUSB HIDで制御。電源サイクルでArduinoをリセット
  するのに使う。`VMAX_MV=5000`のハードガード付き(このハードは5V専用)
- `overnight_mmc3.py` — 失敗するたびDP100で電源サイクルしながら無人で試す
  リトライループ。成功したらRetroArchで実際に起動してスクリーンショットを
  撮り、内部チェックだけでは見抜けない偽の成功を防ぐ
